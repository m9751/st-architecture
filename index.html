0 The Platform / Tenant Model NEW v3.2

The whole system has a name: Smokin Stack v1.0. It is a personal operating system with applications running on it. Some components are platform — domain-agnostic, hardened once, hosting many. Some are tenants — self-contained applications that use the platform to do their job. Sub-pieces have their own version numbers (AOF v1.4, ST v3.3, WD, TP v2, etc.); the umbrella version moves only when the shape changes — a new tenant, a new platform component, or a structural rewrite. Reading the page top to bottom, the platform-vs-application story should be visible in 30 seconds.

Platform
Domain-agnostic infrastructure. Hardens once, hosts many. Observes every tenant. Survives any single application being retired.
  • Claude Code OS Rules · 20 enforcement hooks · skill router (1,384 cataloged) · session lifecycle · MCP fabric (16+) · memory/handoff protocols.
  • smokin-ops xuvdcygqyuajtlpavafr System-of-record for runs, audit, telemetry, KB, decisions, build artifacts. Schemas: kb · runs · audit · telemetry · tp · build.
  • Smokin Decision Adversarial Judge / verdict engine. Railway backend + Vercel frontend. Called by any tenant via POST /debate.
  • Smokin Semantic Layer v1 Deterministic decision functions in Postgres (ICS classify · HRRP exposure · engagement gate). Pure logic, no model calls.
  • Thinking Partner v2 (TP) Decision capture + state machine for the operator. Lives in smokin-ops.tp; consumes Smokin Decision. Both a tenant of smokin-ops and a platform service for the operator — that duality is the model becoming self-aware.
Tenants
A self-contained application running on the platform. Each owns its Supabase project, its scoring/logic engines, and its own brand surface. Tenants never cross the streams. The platform does.
  • SmokinTerritory — Application 1 cnplogkxbjecdeeritdl Sales / territory engine. 865 healthcare accounts, 469 parent orgs. Six scoring engines (TYS · CHPS · BHPS · PSPS · RMS · Golden Record). Brief API · campaigns · proposals · POVs.
  • Whiskey Down — Application 2 wwmhnjfmrbqemeygygcn FX research / trading desk. Backtests, candidates, USDCAD blotter, fusion runs, published_ideas store. Validates that the platform model holds across a totally different domain.
  • Application 3 — TBD Reserved slot. Proves the platform is genuinely transferable. Not yet picked. The empty slot is the point — the architecture is ready for it.
Why this split matters. A platform with one tenant is just an application with extra steps. A platform with two tenants in different domains (sales + trading) is a platform under test. A platform with three tenants — where the third is something genuinely different — is a transferable system. v3.2 makes the model visible on the page so the next decision (what's Application 3?) can be made with the architecture in front of you, not in your head.

1 Architecture Overview

SmokinTerritory is a territory intelligence platform built to surface the right healthcare accounts at the right time for MuleSoft pipeline generation. It combines a Supabase PostgreSQL data warehouse (865 accounts, 469 unique parent organizations), a Vercel-hosted dashboard, GitHub Actions signal pipelines, and a Claude Code AI layer with 20 enforcement hooks, 5 specialist agents, 1,384 cataloged skills, and 16+ MCP server connections — all coordinated to reduce pipeline research from hours to minutes.

The architecture has three layers: a compute layer (Vercel for frontend/APIs, GitHub Actions for pipeline orchestration, Railway for persistent services), a data layer (three Supabase projects for structured CRM/trading/observability data, Qdrant for vector search, Hindsight for cross-session AI memory), and an AI infrastructure layer (Claude Code orchestrating specialized agents via hooks, skills, and MCP tools). The second Supabase project (Whiskey Down) handles trading/backtesting in isolation; the third (smokin-ops, schema TBD) is the system-of-record for runs/audit/observability. All three sit behind a hard zero-cross-join boundary and share a unified PR-gated migration workflow.

Six scoring engines — TYS v7.6_threshold_recal, CHPS v1.1, BHPS v1.0, PSPS v1.4, RMS v1, and Golden Record v2 — produce tier assignments and composite scores. The Smokin Semantic Layer v1 (Feature Functions v1, shipped 2026-04-25) sits alongside as a deterministic decision-function layer (ICS classify · HRRP exposure · engagement gate); pgvector gate closed NO-GO 2026-05-06 — engine-folding deferred indefinitely.

Staging Branches Workflow NEW v2 · 2026-04-26

Schema changes flow through PR review with auto-spun Supabase preview branches that catch bad migrations before production. Identical workflow across all 3 projects.

  1. Local: cd ~/repos/<repo> && supabase migration new <name> — edit the new file in supabase/migrations/.
  2. Push to topic branch + open PR against main.
  3. Supabase auto-creates a preview branch, applies all migrations, posts the Supabase Preview status check on the PR.
  4. Required check enforces it: main ruleset requires Supabase Preview + linear history + squash/rebase. Failed migration = mergeStateStatus: BLOCKED.
  5. Merge to main triggers production deployment; new migration recorded in schema_migrations.

Trigger phrases — ST + WD: "resume staging branches" · smokin-ops: "resume staging branches smokin-ops". Verified end-to-end 2026-04-26 (no-op PR PASS, broken-migration PR BLOCKED on all three).

HARD RULES — Never violate:

1. Never cross the streams. ST / WD / smokin-ops tables are never queried across project boundaries.

2. No cross-project SQL joins. Zero dblink, zero foreign data wrapper, zero table references across project IDs in any SQL statement.

3. Routing is by env vars + Layer 0 vocabulary. WD = WD_SUPABASE_URL; smokin-ops vocabulary = SoR / runs log / audit log / observability / ai-ops. Pass project_id explicitly on every Supabase MCP call.

4. Never dual-write deliverables. Each project has its own deliverables table. WD builds → WD project. ST builds → ST project. (smokin-ops logs on ST until it has a table.) If a row is found on the wrong project, migrate it then DELETE the original.

5. DDL via PR only. No live apply_migration on production projects — go through the staging-branches workflow.

6. Ambiguous task? ASK Michael which project — never guess.
